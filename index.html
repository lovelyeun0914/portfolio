문제 발견

운영팀이 수기 엑셀로 월세·보증금·연체이자를 계산하며 겪는 불편을 직접 제보. 매달 30분씩 반복되는 수작업과 실수 리스크를 확인.

판단

정산 항목이 매일 자정 기준으로 전체 계약에 일괄 반영되는 구조라 실시간 계산보다 배치 처리가 적합하다고 판단. 운영팀과 예외 케이스(연체·중도 정산 등)를 조율하며 배치 로직의 처리 범위를 확정.

구현

  • 수기 엑셀로 계산하던 월세·보증금·연체이자 정산을 백엔드 로직으로 코드화
  • 매일 자정 CRON이 전체 계약의 정산 내역을 자동 갱신하도록 설계
  • 정산 결과를 DB와 관리자 대시보드에 실시간 반영, HTML 리포트 자동 생성

시스템 구조

[매일 자정 CRON 실행]
        │
        ▼
[정산 서비스 로직]
 ├─ 납부 데이터 수집 (Bill, History)
 ├─ 계약 상태 조회 (Contract)
 ├─ 연체이자 / 지연이자 계산
 └─ 반환금 정산
        │
        ▼
[정산 결과 저장 · 리포트 생성]
 ├─ DB Update (bill, cost, report)
 └─ 관리자 대시보드 반영

계산 로직

연체이자(납부금액 − 실납부금액) × 이자율
지연이자(월세지연일수 − 반환소요일수) × 일별이자
반환금보증금 − 추가납부금(청구액 − 실납부액) − 패널티 − 기타비용 − 연체이자 + 지연이자

검증 · 트러블슈팅

첫 테스트에서 자동 정산 결과가 기존 정산과 여러 곳에서 어긋났고, 원인을 한 단계씩 좁혀 맞췄습니다.

  1. 종이계약 누락 : 전자계약과 종이계약이 섞여 시스템에 없던 계약을 찾아 DB로 이관
  2. 재계약 미연결 : 재계약이 본계약과 연결되지 않아 정산이 끊김 → 5,000건 이상의 계약 중 유효기간 내 계약을 추려 재계약 이력을 연결
  3. 산식 점검 : 반환금은 여러 비용 항목이 얽혀 최종 금액만으로는 오류 위치를 알 수 없음 → 항목별 DB 기록을 하나씩 대조
  4. 조회 성능 : 데이터가 쌓여 다중 JOIN 조회가 느려짐 → CTE·서브쿼리로 중간 집계를 분리해 재구성
  5. 배치 안정성 : 비정상 데이터 하나로 전체 정산이 멈출 위험 → 예외 처리를 단계별로 모듈화해 문제 건만 건너뛰도록 설계

문제 발견

운영팀으로부터 재계약·갱신·중도퇴실 처리 과정의 불편을 전달받아 문제 파악.

판단

계약 상태·납부·정산 정보를 연결하는 상태값 설계를 여러 안으로 검토. 재계약 시 과거 이력을 어디까지 연결할지 결정하는 과정에서 시스템에 등록되지 않은 계약 건들을 발견해 직접 조사·데이터화. 상태값·예외케이스는 운영팀과, 기존 시스템 연동 방식은 개발팀과 조율.

구현

  • 계약 생성·재계약·중도퇴실 과정을 자동화하고 상태·납부·정산 정보를 연결
  • 계약 변경 시 납부내역·보증금·정산정보가 즉시 동기화되도록 설계
  • 과거 계약과 재계약 내역을 한 화면에서 확인하도록 관리자 UI 개선

문제 발견

호스트(임대인)가 이미지 업로드·매물 정보 관리 불편을 계속 호소해 문제 파악.

문제 재정의

처음 과제는 이미지 업로드 안정화였지만, 운영팀을 통해 호스트 문의를 확인해 보니 실제 불편은 업로드가 아니라 이미지 편집과 위치 정보 입력이었습니다. 호스트가 직접 처리하지 못해 운영팀이 이미지를 대신 등록하고 있었고, 과제를 ‘호스트가 스스로 관리할 수 있게 만드는 것’으로 다시 정의했습니다.

판단

기획팀은 개발 리소스를 이유로 기존 범위 유지를 원했습니다. 운영팀이 대리 등록에 쓰는 시간을 정리해 기능 추가가 오히려 운영 업무를 줄인다는 근거를 제시하고, 직접 등록·편집하는 핵심 기능부터 만들고 나머지는 다음 단계로 나누는 안으로 합의했습니다. 지하철 정보는 수동 입력 대신 카카오 Local API 자동화를 택했습니다.

구현

  • Dropzone 기반 업로드에 자동 압축·크롭·정렬·S3 저장을 붙인 이미지 라이브러리 개발
  • 드래그 정렬 시 순서와 대표 이미지 뱃지가 자동 갱신되도록 구현
  • 카카오 로컬 API 카테고리 검색으로 좌표 기준 500m 내 지하철역 자동 표시
  • User/Host 서버 구조 차이에 따른 라이브러리 예외 처리

현장 이슈 대응

운영자 한 명의 PC에서만 이미지가 저장되지 않는 문제가 생겼고, 다른 환경에서는 재현되지 않았습니다. 그 운영자의 업무가 끝난 뒤 해당 PC에서 직접 테스트하며 원인을 좁혀, 브라우저 확장 프로그램이 CORS 요청을 차단하고 있음을 찾았습니다. 대체 브라우저 사용 가이드를 매뉴얼로 만들어 운영팀 전체에 배포했습니다.

문제 발견

배관·하수구 막힘 접수를 인근 기사에게 연결하는 앱으로, 고객사는 관리자가 기사를 직접 배정하고 있었습니다. 접수마다 등록된 기사 전체를 불러와 반복문으로 거리를 계산하는 구조라, 기사가 늘수록 푸시 발송이 늦어질 수 있었습니다.

판단

거리 계산을 애플리케이션이 아니라 DB에서 처리하면 반경 내 기사만 바로 추릴 수 있다고 판단했고, 이 구조라면 관리자 수동 배정 대신 인근 기사에게 자동으로 배차를 요청할 수 있다고 고객사에 제안했습니다. 결제와 알림톡은 외부 업체 연동 규격을 먼저 확인해 일정이 막히지 않게 했습니다.

구현

  • 신청 주소와 기사의 위도·경도를 저장하고, MySQL 삼각함수(cos·sin) 쿼리로 반경 내 기사만 조회
  • 인근 기사에게 자동으로 배차를 요청하는 구조와 기사·정산 관리자 페이지 구현
  • 이노페이 문자결제·간편결제 연동, 결제 완료 결과값으로 후속 처리와 DB 기록이 정확한지 테스트로 검증
  • 세종텔레콤 알림톡 연동, Android·Swift 네이티브 기능으로 상황별 알림음 설정

현장 이슈 대응

운영 중 일부 기사에게만 알림이 가지 않는 문제가 생겼습니다. 기기 환경을 확인해 Android 버전에 따라 알림 채널(Notification Channel) 지원 여부가 달라 생긴 문제임을 찾았고, 버전별로 처리 방식을 맞춰 해결했습니다.
